# Справочник

Подробности, которые не поместились в [README](../README.md): тулы и песочница, политика разрешений, скиллы и память, MCP-сервер и поиск, проверка опоры ответа, рассуждения, ключи, цены, прокси, сервер и его API, команды и структура проекта. Решения и история этапов — в [plan.md](plan.md).

## Требования

- Node.js 22.13 или новее, рекомендуется 24 (указана в `.nvmrc`).
- pnpm: достаточно выполнить `corepack enable`, нужная версия pnpm указана в `package.json`.
- Ключ DeepSeek API — понадобится с этапа 1. Подойдёт и любой другой OpenAI-совместимый API.

## Быстрый старт

```bash
pnpm install
cp .env.example .env   # заполнить DEEPSEEK_API_KEY
pnpm chat "Сколько дней отпуска положено по регламенту? Запиши ответ в notes/vacation.md"
```

С флагом `--verbose` под каждой строкой печатается полное событие в JSON:

```bash
pnpm chat --verbose "вопрос"
```

Каждая сессия записывается в `traces/` — формат описан в [docs/events.md](events.md).

## Реестр моделей

В форме новой сессии модель и reasoning effort выбираются одинаковыми селекторами перед запуском, выбор запоминается в браузере. Селекторы расположены под настройками харнесса, которые раскрыты по умолчанию при каждом открытии формы; их можно временно свернуть. Модель и поиск ограничены шириной 330 px, effort — 180 px; в узкой панели поля переносятся и сжимаются. В шапке сессии и списках записей видны модель и провайдер. В «Исследовании» — фактический URL и заголовки запроса с замаскированным ключом.

Текущий блок `model` — модель по умолчанию (`default`). Он работает без изменений, даже если `providers` и `models` отсутствуют. В начальном конфиге дополнительно есть GLM 4.6 и Claude Sonnet 4.5 через OpenRouter, GPT-5 mini через OpenAI и Qwen3 8B через Ollama.

В `.env` ключ задаётся один раз на провайдера:

```dotenv
DEEPSEEK_API_KEY=ваш-ключ
OPENROUTER_API_KEY=ваш-ключ
OPENAI_API_KEY=
```

Один ключ OpenRouter используется всеми моделями этого провайдера. Пустые ключи допустимы: сервер и просмотр записей работают, но модель нельзя выбрать. Наличие ключа означает только наличие настройки — доступность API проверяется при запросе. Ссылки `keychain:имя-сервиса` продолжают работать. Ключи читаются сервером, браузер получает только имя переменной и признак её заполнения. После изменения конфига или `.env` перезапустите сервер.

Пример добавления провайдера и модели в `harness.config.json` рядом с существующим `model`:

```json
{
  "providers": {
    "openrouter": {
      "providerName": "OpenRouter",
      "baseUrl": "https://openrouter.ai/api/v1",
      "apiKeyVariable": "OPENROUTER_API_KEY",
      "dialect": "openrouter"
    }
  },
  "models": {
    "glm-4.6": {
      "provider": "openrouter",
      "model": "z-ai/glm-4.6",
      "label": "GLM 4.6"
    }
  }
}
```

Вместо `provider` модель может содержать `baseUrl`, `apiKeyVariable` и `dialect` непосредственно. `apiKeyVariable: null` — явно без ключа и без заголовка Authorization, например для Ollama или LM Studio. Включение локальной модели не запускает её сервер и не скачивает веса; для примера Qwen нужны работающий Ollama и `ollama pull qwen3:8b`.

Диалекты: `deepseek` сохраняет прежние `thinking`, `reasoning_content`, кэш и расчёт цены по тарифам; `openrouter` использует `reasoning`, сохраняет reasoning-блоки между tool calls, читает цену из `usage.cost`; `openai` — общий OpenAI-совместимый формат. Для прямых reasoning-моделей нужно явно задать `reasoningStyle: "openai"`; для GPT-5 mini также `outputTokenParameter: "max_completion_tokens"`. Это адаптер Chat Completions, а не поддержка произвольных API вроде Anthropic Messages или OpenAI Responses.

Общие `requestTimeoutMs`, `maxOutputTokens`, `stream`, `reasoningStyle`, `defaultReasoningEffort`, `outputTokenParameter` и `requestExtras` можно задать у провайдера и переопределить у модели. Если таймаут и лимит ответа не заданы, берутся из текущего `model`. DeepSeek-специфичные beta URL, logprobs и параметры запроса другим моделям не наследуются.

`capabilities` описывает возможности для отображения: `reasoning`, `cache`, `logprobs` — `true`, `false` или отсутствуют («нет данных»). `reasoningEfforts` ограничивает доступные уровни; `defaultReasoningEffort` должен входить в этот список. Уровень `off` для OpenAI преобразуется в `none`, у DeepSeek и OpenRouter отключает reasoning. Неподдерживаемые уровни не добавляйте в список. Для API без настройки reasoning используйте `reasoningStyle: "none"` — effort не передаётся.

Стоимость OpenRouter берётся из ответа в USD; если `usage.cost` нет, цена неизвестна, а не нулевая. Разбивка по input/output не выдумывается. Для остальных API используются записи `prices` по точному API ID модели; без тарифа стоимость неизвестна. Кэш нормализуется из полей провайдера; правила его учёта могут различаться. Оценка бюджета prompt до ответа по-прежнему настроена на DeepSeek и для других моделей приблизительная.

Первый этап ограничен обычными сессиями, включая диалог и включённых субагентов: все используют выбранную модель. Для именованной модели compaction также выполняется на ней; глобальный `context.compactionModel` относится к провайдеру по умолчанию. Ветки поддерживают выбор модели исходного шага или другой модели реестра; CLI `pnpm branch` принимает `--model` и `--effort`. Evals поддерживает `--model` / `--models`, общий `--effort` и отдельный `--judge-model`. Остальные CLI-команды, лаборатории и оркестрация продолжают использовать текущий `model`. Старые трейсы не требуют новых полей; новые `modelKey`, `modelLabel` и `dialect` добавляются при наличии настройки.

В Evals список `--models default,glm-4.6` образует матрицу с `--configs tool,auto`: четыре конфигурации вида `tool@default`, `auto@default`, `tool@glm-4.6`, `auto@glm-4.6`. Без выбора модели сохраняются старые имена и DeepSeek по умолчанию. Ключи и поддержка effort проверяются до первого запроса. `--effort` явно переопределяет effort всех вариантов, включая `tests-max` арены; без флага действует effort варианта либо выбранной модели. Неподдерживаемые уровни не понижаются автоматически.

У судьи отдельный выбор `--judge-model` (по умолчанию `default`), общий для всех попыток, с effort `off`. Если выбранная модель не поддерживает `off`, прогон останавливается до запуска. `--no-judge` позволяет сравнивать другие модели без ключа DeepSeek; проверки с рубрикой остаются без вердикта. Отчёт хранит снимок модели, провайдера и effort каждой конфигурации, фактические имена моделей из ответов попытки и модель судьи. Лаборатория показывает эти данные и старые отчёты без миграции; запуск Evals остаётся через CLI.

Форматы сверены с [OpenRouter API](https://openrouter.ai/docs/api/reference/overview), [reasoning и сохранением его блоков](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens) и [публичным каталогом моделей](https://openrouter.ai/api/v1/models) 30.10.2026. Каталог и возможности провайдеров могут меняться.

## Песочница и тулы

Агент работает с файлами только в папке `workspaces/demo/`. При первом запуске она создаётся из примеров `examples/workspace/` — документов вымышленной компании «Кедр Софт». Выйти за пределы песочницы тулы не дают.

В сессии без демо-проекта у агента своя пустая папка на каждую сессию — `workspaces/blank/<имя трейса>`, например `workspaces/blank/2026-10-26T20-00-00_abcd1234`: написанное в одной сессии не перезапишет следующая. Ветка такой сессии начинает с копии её папки — с тем, что было в ней к концу исходной сессии. Копии проектов Код-арены — в `workspaces/arena/`.

Песочница сохраняется между запусками: агент увидит заметки, которые написал в прошлых сессиях. Чтобы начать с чистого листа, добавьте флаг `--fresh` — папка будет пересоздана из примеров:

```bash
pnpm chat --fresh "вопрос"
```

| Тул                             | Что делает                                                           |
| ------------------------------- | -------------------------------------------------------------------- |
| `list_files`                    | показывает файлы и папки                                             |
| `read_file`                     | читает файл (длинные файлы обрезаются)                               |
| `search_files`                  | ищет текст во всех файлах без учёта регистра                         |
| `write_file`                    | создаёт или перезаписывает файл                                      |
| `delete_file`                   | удаляет файл — только с разрешения пользователя                      |
| `fetch_url`                     | загружает страницу и возвращает её основной текст в Markdown         |
| `web_search`                    | ищет в интернете через Yandex Search API или Tavily (если есть ключ) |
| `load_skill`, `read_skill_file` | инструкция скилла и его файлы (раздел «Скиллы» ниже)                 |
| `memory`                        | память между сессиями в `memory/` (раздел «Память» ниже)             |
| `update_progress`               | план задачи со статусами шагов — харнесс пишет `progress.md`         |

Лимит шагов агента за один ход — `agent.maxIterations` в `harness.config.json`.

**Политика разрешений.** Тулы только объявляют, что делают (`read`, `write`, `delete`, `network`) и с чем работают — пути и адреса. Решает харнесс по разделу `permissions` в `harness.config.json`, в таком порядке:

1. правила по аргументам (`rules`) — первое подходящее; в примере запрещены запись и удаление в `regulations/**`;
2. правило для конкретного тула (`tools`);
3. класс действия (`effects`): по умолчанию чтение, запись и сеть разрешены, удаление — спросить;
4. решение по умолчанию (`defaultDecision`) — для тулов, которые не объявили, что делают.

Если решение «спросить», харнесс спрашивает в терминале: «Разрешить? [y/N]». Каждое решение со всеми проверками записывается в трейс как `permission_evaluated`.

**Веб.** `fetch_url` загружает только http и https и по умолчанию не ходит на `localhost` и адреса локальной сети — чтобы модель не добралась до сервисов на вашем компьютере (`webFetch.allowPrivateNetwork` в конфиге).

**Поиск.** Провайдер выбирается в `harness.config.json` (`search.provider`) или флагом на один запуск:

```bash
pnpm chat --search yandex "вопрос"
pnpm chat --search tavily "вопрос"
```

| Провайдер         | Ключи в `.env`                                     | Условия                                                                                                                 |
| ----------------- | -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Yandex Search API | `YANDEX_SEARCH_API_KEY`, `YANDEX_SEARCH_FOLDER_ID` | [AI Studio](https://aistudio.yandex.ru): API-ключ и ID каталога, нужен платёжный аккаунт; около 0,5 ₽ за поиск днём     |
| Tavily            | `TAVILY_API_KEY`                                   | [app.tavily.com](https://app.tavily.com): 1000 запросов в месяц бесплатно; из некоторых сетей работает только через VPN |

Если ключей выбранного провайдера нет, `web_search` не регистрируется, а в консоли написано почему.

## Скиллы

Скилл — инструкция для отдельной задачи: папка в `skills/` с `SKILL.md` и, если нужно, дополнительными файлами. Формат — как у [Agent Skills](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview) Anthropic. В system prompt харнесс кладёт только каталог — имя и описание каждого скилла; инструкцию модель загружает тулом `load_skill`, когда задача подходит под описание, а шаблоны и справки читает `read_skill_file`. Так скилл не занимает prompt, пока не нужен.

| Скилл             | Что делает                                                               |
| ----------------- | ------------------------------------------------------------------------ |
| `policy-answer`   | ответ по регламенту: действующая редакция, дословная цитата, расхождения |
| `incident-review` | разбор инцидента по шаблону компании                                     |
| `meeting-summary` | сводка встречи — только по команде пользователя                          |

Режимы — в разделе `skills` файла `harness.config.json`: по умолчанию модель выбирает сама; `always` — инструкция в system prompt с самого начала; `manual` — скилла нет в каталоге, его загружает пользователь командой в начале вопроса:

```bash
pnpm chat "/meeting-summary общее собрание 20 октября"
```

Подробнее о формате и своих скиллах — `skills/README.md`.

## Память

Память агента живёт между сессиями — в папке `memory/` песочницы; модель видит её как `/memories` и работает с ней тулом `memory`, как в [memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool) Anthropic: `view`, `create`, `str_replace`, `insert`, `delete`, `rename`. Главный файл — `/memories/memo.md`: харнесс кладёт его в system prompt в начале каждой сессии, поэтому агент помнит договорённости и незаконченные дела без лишних шагов. Чтение и запись памяти разрешены, удаление — с вопросом пользователю. `--fresh` пересоздаёт песочницу вместе с памятью.

Для задач из нескольких шагов у агента есть план: тулом `update_progress` он присылает цель и шаги со статусами, харнесс проверяет их (в работе — не больше одного шага) и пишет `progress.md` в песочницу. План живёт в рамках сессии.

## MCP-сервер базы знаний

В `packages/mcp-server` — MCP-сервер с базой знаний «Кедр Софт»: 30 документов в `packages/mcp-server/data/` (регламенты, проекты, протоколы встреч, FAQ, разборы инцидентов, справочник сотрудников). Тулы сервера:

| Тул               | Что делает                                                      |
| ----------------- | --------------------------------------------------------------- |
| `search`          | ищет документы по словам с учётом окончаний, вес заголовка выше |
| `semantic_search` | ищет фрагменты документов по смыслу, с оценкой сходства         |
| `read_document`   | возвращает документ целиком, с датой и владельцем               |
| `list_documents`  | показывает каталог документов, можно по типу                    |

Харнесс запускает серверы из раздела `mcpServers` в `harness.config.json` подпроцессами и говорит с ними по stdio. Модель видит их тулы с префиксом сервера: `kedr__search`. Сервер присылает инструкции — харнесс добавляет их в системный промпт.

Каждое сообщение JSON-RPC между харнессом и сервером записывается в трейс (`mcp_message`), строки из stderr сервера — тоже (`mcp_server_log`). В консоли видно рукопожатие: `initialize` → `notifications/initialized` → `tools/list`, а дальше `tools/call` на каждый вызов.

**Доверие к пометкам.** MCP-тул может пометить себя «только чтение» (`readOnlyHint`) — но пометку пишет автор сервера. Харнесс учитывает пометки, только если у сервера `trustAnnotations: true`; иначе тулы сервера получают `permissions.defaultDecision` — по умолчанию «спросить». Своему серверу мы доверяем, чужому — нет.

Ключи из `.env` сервер не получает: только базовые переменные (`PATH`, `HOME` и т. п.) и те, что перечислены в `environmentVariables`.

**Поиск по смыслу.** Документы нарезаны на фрагменты около 700 символов, каждый фрагмент превращён локальной моделью [multilingual-e5-small](https://huggingface.co/intfloat/multilingual-e5-small) в вектор из 384 чисел. Запрос тоже превращается в вектор, и `semantic_search` возвращает фрагменты с самыми близкими векторами. Так можно найти ответ, сформулированный другими словами: в регламенте об отпусках нет слова «отдыхать», и поиск по словам на вопрос «сколько можно отдыхать» его не найдёт.

Модель (около 120 МБ) один раз скачивается с huggingface.co отдельной командой — MCP-сервер сам ничего не скачивает:

```bash
pnpm rag-index
```

Команда скачивает модель в `.cache/embeddings/models/` в корне проекта, считает векторы фрагментов и сохраняет их в `.cache/embeddings/knowledgeBaseVectors.json`. Кэш общий: модель нужна и MCP-серверу, и харнессу (проверка опоры ответа, этап 5b), а код для неё — в пакете `packages/embeddings`. При следующих запусках векторы берутся из кэша; изменился документ — пересчитываются только его изменившиеся фрагменты. Если модели нет, `semantic_search` отвечает ошибкой с подсказкой запустить эту команду, а остальные тулы работают как обычно.

MCP-сервер строит индекс в фоне после старта, чтобы рукопожатие MCP не ждало модель. Ход построения виден в консоли как журнал сервера.

**Сравнение способов поиска.** Команда задаёт одни и те же вопросы трём поискам — по словам, по смыслу и гибридному — и показывает первую пятёрку документов каждого рядом, отмечая нужные:

```bash
pnpm compare-search                          # 20 вопросов с известными ответами и итог
pnpm compare-search "как оформить отпуск"    # своя выдача по любому вопросу
```

Гибридный поиск объединяет две выдачи по местам, а не по оценкам — оценки несравнимы (число совпадений слов против косинуса векторов). Документ получает 1 / (60 + место) от каждой выдачи; способ — Reciprocal Rank Fusion ([Cormack, Clarke, Büttcher, 2009](https://doi.org/10.1145/1571941.1572114)). Поиск по смыслу находит фрагменты, поэтому для сравнения у документа берётся его лучший фрагмент. Вопросы и нужные документы — в `packages/mcp-server/src/searchComparison/searchQuestions.ts`. Нужна скачанная модель (`pnpm rag-index`).

**Кто ищет: модель или харнесс.** По умолчанию модель сама решает, вызывать ли `semantic_search`. С флагом `--retrieval auto` харнесс до первого запроса к модели сам ищет по смыслу по вопросу пользователя и кладёт найденные фрагменты в сообщение пользователя — с пометкой, что это данные, а не инструкции. Тулы поиска у модели остаются, и видно, ищет ли она дальше сама:

```bash
pnpm chat "сколько дней можно отдыхать в году"                    # модель ищет сама
pnpm chat --retrieval auto "сколько дней можно отдыхать в году"   # харнесс подмешивает найденное
```

Третий режим — `--retrieval rewrite`: харнесс сначала просит модель переписать вопрос в поисковый запрос (служебный запрос без тулов), ищет по нему и подмешивает найденное. Вместе три режима — урок «кто формулирует запрос»: пользователь (`auto`), модель по просьбе харнесса (`rewrite`) или модель сама, решая и когда искать (`tool`). На «удалёнка» видно, зачем это: словами пользователя поиск по смыслу не находит старый FAQ, а развёрнутым запросом — находит.

```bash
pnpm chat --retrieval rewrite "удалёнка"   # строка «Query для поиска составила модель: …»
```

Режим по умолчанию, тул и число фрагментов — в разделе `retrieval` файла `harness.config.json`. Тул для одного запуска меняется флагом: `--retrieval auto --retrieval-tool kedr__hybrid_search` — харнесс подмешает гибридный поиск. Тул `hybrid_search` объединяет поиск по словам и по смыслу так же, как `pnpm compare-search`, и возвращает лучший фрагмент каждого документа с местами в обеих выдачах. Модель его не видит: он в списке `hiddenTools` у сервера в `harness.config.json`, и вызывать его может только сам харнесс. Так экспонат не меняет стенд — у модели тот же список тулов и та же инструкция сервера.

**Повторные прогоны.** Модель недетерминирована: один запуск может оказаться и удачным, и неудачным. Команда задаёт шесть вопросов по нескольку раз в каждом варианте — `tool` (модель ищет сама), `auto` (харнесс ищет словами пользователя), `rewrite` (харнесс ищет запросом, который составила модель); по флагу `--variants` есть ещё `hybrid` (как `auto`, но гибридным поиском) — и сводит медиану и разброс. В строке каждого прогона видно, по какому запросу искал харнесс:

```bash
pnpm compare-runs                           # варианты tool, auto, rewrite: 6 вопросов × 3 × 3 = 54 сессии, около 5–6 центов
pnpm compare-runs --runs 5                  # по 5 прогонов
pnpm compare-runs --question 2              # только второй вопрос
pnpm compare-runs --variants tool,hybrid    # только эти варианты
```

В таблице — запросы к модели, тулы, которые попросила модель, input-токены, доля cache hit, `cache warm` — был ли prompt cache прогрет уже к первому шагу агента (то есть чужой сессией — такой прогон дешевле не из-за режима), стоимость, прочитала ли модель нужный документ целиком, назвала ли его в ответе и сказала ли о противоречии (грубо, по словам в ответе). Варианты чередуются, чтобы прогретый кэш промпта доставался всем поровну. У каждого прогона свой трейс в `traces/` и своя временная рабочая папка из примеров — ваша `workspaces/demo/` не меняется. Действия, требующие разрешения, в прогонах запрещаются: спросить некого.

Запустить сервер отдельно, например для MCP Inspector: `node packages/mcp-server/dist/main.js` после `pnpm build`.

## Проверка ссылок ответа

Модель может сослаться на источник, которого не читала. Команда проверяет это по трейсу — без модели, детерминированно:

```bash
pnpm check-grounding traces/<файл>.jsonl
```

Для каждой ссылки в ответе (id документа или путь в обратных кавычках, адрес страницы) видно, что модель на самом деле получила:

| Значок | Уровень                  | Каким тулом                                                                |
| ------ | ------------------------ | -------------------------------------------------------------------------- |
| ✓      | прочитан целиком         | `read_document`, `read_file`, `fetch_url`                                  |
| ~      | только фрагмент в выдаче | `search`, `semantic_search`, `hybrid_search`, `web_search`, `search_files` |
| !      | только строка в каталоге | `list_documents`, `list_files`                                             |
| ✗      | не встречался в трейсе   | —                                                                          |

Неудачный вызов (ошибка, отказ, запрет политики) не засчитывается: модель ничего не получила. Ссылки в свободном тексте без кавычек проверка намеренно не ищет, чтобы не угадывать.

Вторая часть отчёта — claims (утверждения) ответа: предложения, пункты списков и строки таблиц; заголовки и подписи разделов пропускаются. Разбиение грубое, и отчёт так и говорит. Для каждого claim с дословной цитатой в кавычках («…» или "…", от трёх слов) проверка ищет эту цитату в текстах, которые модель получила по трейсу: результаты тулов и найденное харнессом до запроса. Сравнение — после нормализации, не меняющей смысла: регистр, ё/е, разметка Markdown, виды тире и пробелов, точка в конце.

```
13. Подтверждение с общего собрания: «Новый регламент удалённой работы действует с июня — три удалённых дня в неделю»…
     ✓ цитата «…» — дословно в событии #30: kedr__search (вызвала модель), snippet
```

У каждого claim — сходство embeddings с ближайшей строкой того, что видела модель, и сама эта строка с документом:

```
10. Ноутбук выдаёт отдел инфраструктуры.
     ≈ 0.878 близко: #25 kedr__read_document (вызвала модель), целиком, regulations/remoteWork — «8. Ноутбук выдаёт…»
```

Порог «близко» — `grounding.similarityThreshold` в `harness.config.json` (по умолчанию 0.87), и он приблизительный. Числа сходства воспроизводимы на одной платформе: на macOS и Linux квантованная модель даёт расхождения в третьем знаке. Сходство отличает «про то же» от «не про то», но не «верно» от «неверно»: выдуманные claims получают около 0.84–0.86, а противоречащие источнику («отпуск 35 дней» при 28) — 0.87–0.91, столько же, сколько верные. Поэтому отчёт всегда показывает само число. Сравнение — со строками, а не с большими кусками: в куске из десятка пунктов нужный факт растворяется. Нужна скачанная модель (`pnpm rag-index`); без неё отчёт строится без сходства и говорит почему.

Значок у каждого claim — самый сильный уровень опоры по проверкам кодом:

| Значок | Уровень                 | Что значит                                                              |
| ------ | ----------------------- | ----------------------------------------------------------------------- |
| ❝      | цитата найдена дословно | все цитаты claim есть в том, что видела модель                          |
| ✗      | цитаты нет в увиденном  | модель приводит цитату, которой в сессии не получала, — самое тревожное |
| ≈      | про то же по сходству   | без цитат, сходство не ниже порога — но «про то же», не «верно»         |
| ?      | далеко по сходству      | повод проверить глазами                                                 |
| ·      | не проверялось          | модели эмбеддингов нет                                                  |

Третий уровень — модель-судья, по флагу, потому что стоит денег: один запрос к модели на каждый claim.

```bash
pnpm check-grounding traces/<файл>.jsonl --judge
```

Судья видит claim и три ближайшие строки из того, что видела модель в сессии, и отвечает: подтверждают (`supported`), противоречат (`contradicted`) или молчат (`notFound`). В отчёте вердикт — отдельной строкой с пометкой «мнение»: судья тоже модель, он недетерминирован и может ошибаться. Запросы судьи и его вердикты пишутся в свой трейс проверки со ссылкой на исходный, а их стоимость видна в конце отчёта. В конце отчёта — claims, где проверка кодом и судья расходятся: «про то же по сходству», а судья видит противоречие, или наоборот. Их и стоит посмотреть глазами.

Попробовать на ответе с ошибками можно на синтетическом трейсе: настоящие события сессии `53863eac`, в ответе которой «до 3 дней» заменено на «до 2 дней», компенсация — на 50 000 ₽ и добавлены выдуманный факт и выдуманная цитата. Он есть только у автора проекта, в `traces/synthetic-53863eac-errors.jsonl`.

## Рассуждения (effort)

Модель может «подумать» перед ответом. Насколько усердно — задаёт уровень `off`, `low`, `high` или `max`. По умолчанию он берётся из `harness.config.json` (`defaultReasoningEffort`), а для одного запуска меняется флагом:

```bash
pnpm chat --effort off "вопрос"   # без рассуждений
pnpm chat --effort max "вопрос"   # максимум рассуждений
```

Сравните токены, время и стоимость на одном и том же вопросе: рассуждения — это токены выхода, самые дорогие.

## Ключ модели

Ключ можно положить в `.env` прямо (`DEEPSEEK_API_KEY=sk-...`), а на macOS — хранить в связке ключей и указать в `.env` только ссылку:

```bash
security add-generic-password -s harness-visualization-deepseek -a "$USER" -w
# в .env:
DEEPSEEK_API_KEY=keychain:harness-visualization-deepseek
```

Советуем завести отдельный ключ под этот проект и держать на балансе небольшую сумму.

## Модель и цены

Модель, адрес API и таблица цен — в `harness.config.json`. По умолчанию — `deepseek-flash`, рассуждения на уровне `high`. Как провайдер управляет рассуждениями, задаёт `reasoningStyle`: `deepseek` или `none`, если провайдер этого не умеет. Подойдёт любой OpenAI-совместимый API: поменяйте `baseUrl`, `model` и `apiKeyVariable`. Цены DeepSeek зависят от времени суток (пиковые и обычные часы), стоимость считается по времени запроса.

## Прокси и VPN

Сервисы доступны по-разному: один — только через VPN, другой через VPN, наоборот, не открывается. Поэтому маршрут выбирается для каждого запроса по адресу хоста — раздел `network` в `harness.config.json`:

```json
"network": {
  "defaultRoute": "proxy",
  "rules": [
    { "description": "Поиск Яндекса работает без VPN — напрямую", "hostPattern": "*.yandex.net", "route": "direct" }
  ]
}
```

- `proxy` — через прокси из `HTTPS_PROXY` или `HTTP_PROXY` (их выставляют VPN-клиенты и корпоративные сети); если прокси в окружении нет — напрямую.
- `direct` — напрямую, даже если прокси задан.
- Правила проверяются по порядку, первое подходящее решает; шаблоны — как в политике разрешений: `api.tavily.com`, `*.yandex.net`.

Маршрут каждого запроса к модели, поисковику и странице записывается в трейс (`network_request`) и виден в консоли: «Сеть: api.deepseek.com → через прокси … (маршрут по умолчанию)». Логин и пароль прокси скрываются. Маршруты применяет сам харнесс через диспетчеры [undici](https://github.com/nodejs/undici) (`ProxyAgent` и `Agent`), поэтому `NODE_USE_ENV_PROXY` для `pnpm chat` не нужен.

## Интерфейс

```bash
pnpm dev
```

Поднимает сервер харнесса и Vite вместе; интерфейс — http://127.0.0.1:5173. Ключ модели — тот же `.env`, что у `pnpm chat`. Запросы к `/api` Vite передаёт серверу, поэтому страница, поток событий и ответы на разрешения идут с одного адреса. Без Vite — `pnpm serve` (ниже): сервер сам отдаёт собранный интерфейс на http://127.0.0.1:4317. `pnpm dev` нужен, когда меняете код интерфейса: правки видны сразу.

**Стартовый экран** — на всю ширину, до 1440 px: вопрос агенту с опциями сессии, рядом — сессии сервера и записанные трейсы с поиском по вопросу, справа — лаборатории и импорт чужой записи («Открыть трейс Claude Code / OpenCode…»). На узком экране — одна колонка: вопрос, лаборатории, списки.

**Шапка** — режим, тема и выезжающая панель с сессиями, трейсами и запуском новой сессии.

- **Режимы:** «Обучение» — со справкой «Что это?» (тексты в `docs/help/`), вводными и выводами; «Исследование» — без учебного слоя, вместо инспектора экран шагов, учебных лабораторий RAG и MCP нет. Переключаются без перезапуска, выбор запоминается в браузере.
- **Тема:** авто, светлая «Индиго», тёмная «Лайм» — тоже запоминается в браузере.

**Плеер** — одинаковый для живой сессии и записанного трейса. Внизу на всю ширину: повтор, пауза, шаги, скорость и лента действий для перемотки. Позиция — в адресе, секунды сессии (`?t=`). Все вкладки показывают события до курсора повтора. Строка токеномики видна на всех вкладках. Справа — колонка «Диалог»: вопросы, ответы и следующий вопрос живой сессии; на узком экране она свёрнута. Вопрос о разрешении приходит с кнопками и обратным отсчётом.

| Вкладка         | Что показывает                                                                                                                                                                                                                                                             |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Поток           | харнесс изнутри анимацией: цикл агента, контекст, политика, retrieval, исполнение тулов; точка идёт по маршруту и возвращается ответом                                                                                                                                     |

## Сервер и поток событий в браузер

```bash
pnpm serve
```

Собирает все пакеты и запускает сервер: на http://127.0.0.1:4317 — собранный интерфейс (`packages/ui/dist`, сервер отдаёт его сам, без Vite), под `/api` — запуск сессий и поток событий. Сервер слушает только `127.0.0.1` на порту из `harness.config.json` (`server.port`, по умолчанию 4317). Авторизации нет: это локальный учебный стенд, а каждая сессия тратит деньги владельца ключа модели.

Лаборатории RAG сервер отдаёт базу знаний, поиск тремя способами, векторы фраз и проверку опоры ответа (`/api/rag/…`); для этого нужна модель эмбеддингов (`pnpm rag-index`).

Отладочная страница — http://127.0.0.1:4317/debug: запуск сессии, поток событий с полным JSON по клику, кнопки «Разрешить» и «Отказать» с обратным отсчётом, записанные трейсы. Это проверка сервера руками, без React и сборки. То же самое можно сделать через curl:

`--noproxy '*'` — на случай, если в терминале задан прокси: без флага curl может отправить запрос к `127.0.0.1` через него и получить пустой ответ.

```bash
# запустить сессию — ответ приходит сразу, с id сессии
curl --noproxy '*' -X POST -H 'content-type: application/json' \
  -d '{"question": "удалёнка", "retrievalMode": "auto"}' http://127.0.0.1:4317/api/sessions

# поток её событий (SSE)
curl --noproxy '*' -N http://127.0.0.1:4317/api/sessions/<id>/events
```

| Маршрут                              | Что делает                                                                                                                                                        |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /api/sessions`                 | запускает сессию: `question` и необязательные `reasoningEffort`, `retrievalMode`, `retrievalToolName`, `searchProvider`, `freshWorkspace` — как флаги `pnpm chat` |
| `GET /api/sessions`                  | сессии этого запуска сервера                                                                                                                                      |
| `GET /api/sessions/:id`              | состояние одной сессии и вопросы о разрешении, ждущие ответа (`pendingPermissions`)                                                                               |
| `GET /api/sessions/:id/events`       | поток событий (SSE): сначала то, что уже было, потом — вживую                                                                                                     |
| `POST /api/sessions/:id/messages`    | следующий вопрос диалога (после `awaiting_question`): `{"text": "…"}`; `POST /api/sessions/:id/finish` — закончить диалог                                         |
| `POST /api/sessions/:id/permissions` | ответ на `permission_requested`: `{"toolCallId": "…", "approved": true}`                                                                                          |
| `GET /api/traces`                    | записанные трейсы из `traces/`: вид (сессия или проверка опоры), вопрос, время, дописан ли до конца, `synthetic` — собран руками                                  |
| `GET /api/traces/:file/events`       | события трейса тем же потоком SSE, что у живой сессии, — сразу все, без исходных пауз                                                                             |

Если на вопрос о разрешении не ответить за `server.permissionTimeoutSeconds` (по умолчанию 120 секунд), действие запрещается: молчание не согласие. Попробовать можно на вопросе, где агенту нужно удалить файл (запись разрешена без вопроса, удаление — с вопросом). Скрипт сам достаёт `toolCallId` из `pendingPermissions`; нужен `jq`:

```bash
U=http://127.0.0.1:4317
S=$(curl --noproxy '*' -s -X POST -H 'content-type: application/json' \
  -d '{"question": "Создай notes/probe.md с текстом «проба», потом удали его"}' $U/api/sessions | jq -r .sessionId)
sleep 10   # подождать, пока агент дойдёт до удаления
T=$(curl --noproxy '*' -s $U/api/sessions/$S | jq -r '.pendingPermissions[0].toolCallId')
curl --noproxy '*' -X POST -H 'content-type: application/json' \
  -d "{\"toolCallId\": \"$T\", \"approved\": true}" $U/api/sessions/$S/permissions
```

Если `T` — `null`, агент ещё не дошёл до удаления: повторите две последние команды.

Формат потока и ответа на разрешение — в [events.md](events.md).

| `pnpm eval --set <набор>`           | Прогон evals: задачи × конфигурации × попытки       |
| `pnpm arena --task <id>`            | Код-арена из терминала; `--verify` — проверка задач |
| `pnpm branch <трейс>`               | Ветка от шага записанной сессии                     |
| `pnpm import-trace <формат> <файл>` | Трейс Claude Code или OpenCode — в наш формат       |
| `pnpm logprobs-probe`               | Проба: что модель отдаёт о вероятностях токенов     |
| `pnpm build`                        | Собирает все пакеты                                 |
| `pnpm typecheck`                    | Проверяет типы TypeScript                           |
| `pnpm lint`                         | Проверяет код ESLint                                |
| `pnpm lint:fix`                     | Исправляет то, что ESLint умеет исправить сам       |
| `pnpm format`                       | Форматирует код Prettier                            |
| `pnpm check`                        | Типы, линтер и форматирование — всё вместе          |
