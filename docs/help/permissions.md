# Разрешения

Прежде чем выполнить tool, харнесс проверяет вызов **политикой** из `harness.config.json` и записывает след решения — `permission_evaluated`: какие проверки сделаны, какая сработала и почему.

## Как принимается решение

- У каждого tool есть **класс действия**: `read`, `write`, `delete`, `network`. По классу политика по умолчанию решает: `allow` — выполнить, `ask` — спросить пользователя, `deny` — запретить.
- **Правила** по путям и хостам уточняют решение: например, «Регламенты — только чтение» запрещает запись в `regulations/**`.
- Возможность действия проверяется до вопроса: про несуществующий файл пользователя не спрашивают.

## Вопрос пользователю

При `ask` харнесс спрашивает (`permission_requested`) и ждёт ответа. Кто решил — в `answeredBy`:

- `user` — ответил пользователь;
- `timeout` — никто не ответил вовремя (по умолчанию 120 секунд);
- `noOneToAsk` — спросить было некого: нет терминала или это тихий прогон `compare-runs`.

Последние два — всегда отказ. Модель получает об этом правду: не «пользователь не разрешил», а «не ответил вовремя» или «спросить было некому» — иначе она решила бы, что пользователь против.

Проверено: 25.10.2026
