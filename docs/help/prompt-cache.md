# prompt cache

Провайдер модели запоминает начало недавних prompt. Если новый запрос начинается так же, эту часть не обрабатывают заново — она приходит **из кэша** и стоит дешевле.

## Как это работает у DeepSeek

- Кэш включён для всех по умолчанию, в запросе ничего указывать не нужно.
- Совпасть должно именно начало: после запроса `A + B` запрос `A + B + C` попадёт в кэш, а `A + C` — нет.
- Сколько токенов пришло из кэша, провайдер пишет в ответе: `prompt_cache_hit_tokens` и `prompt_cache_miss_tokens`. Харнесс переносит их в `usage` как `inputCacheHitTokens` и `inputCacheMissTokens`.
- Кэш работает «best effort» — попадание не гарантировано. Неиспользуемый кэш очищается, обычно через несколько часов или дней.
- Попадание в кэш у `deepseek-flash` в 50 раз дешевле промаха: $0.003 против $0.15 за 1M input tokens вне пиковых часов.

## Чем прогрет кэш

Провайдер говорит **сколько** токенов пришло из кэша, но не **кто** их туда положил. Поэтому интерфейс объясняет осторожно:

- в пределах prompt предыдущего шага — каждый шаг заново отправляет весь контекст, и его начало уже в кэше;
- больше всего prompt предыдущего шага — кэш прогрел не только он: такое же начало недавно отправляли ещё — прошлые сессии с тем же вопросом или другая программа с тем же ключом;
- у первого запроса сравнить не с чем.

«Прогрет» — когда из кэша не меньше 10 % prompt. Это соглашение харнесса, а не провайдера: небольшое попадание бывает у любого запроса, потому что начало у многих prompt общее.

Прогретый кэш важен при сравнениях: два одинаковых прогона стоят по-разному, если перед одним кэш прогрела предыдущая сессия.
